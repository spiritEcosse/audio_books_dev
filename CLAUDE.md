# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Tauri 2 desktop app (Rust backend + React 19/TypeScript/Vite frontend, pnpm) for turning stories into illustrated, narrated audiobook videos. The user chats with Claude about one story; Claude edits the story text and splits it into scenes (narrated text + English image prompt). UI strings and many prompts are in Russian. The README is the unmodified Tauri template.

## Commands

- `pnpm install`
- `pnpm tauri dev` — run the full app (Vite dev server + Rust backend). `pnpm dev` alone runs only the web frontend, where `invoke` calls will fail.
- `pnpm build` — `tsc && vite build` (type-check + frontend bundle). This is the only frontend check; there is no linter or test runner configured.
- `pnpm tauri build` — production bundle.
- Rust: `cd src-tauri && cargo check` / `cargo build`. There are no tests yet; `cargo test <name>` runs a single one once `#[test]`s exist.

`.env` (see `.env.example`) holds `ELEVENLABS_API_KEY` and `ANTHROPIC_API_KEY`. Optional `CLAUDE_BIN` env var overrides the `claude` binary path.

## Architecture

Frontend (`src/`) is thin: `api.ts` holds the TypeScript types and typed wrappers around Tauri `invoke`; components just render state. All logic lives in Rust commands registered in `src-tauri/src/lib.rs`, which also holds `AppState` (a `Mutex<Connection>` plus the workspace dir).

Design points that span several Rust modules:

- **Claude is driven through the `claude` CLI, not the API** (`claude.rs`). It is spawned headless (`-p --output-format json`) with tools, user settings, MCP servers and slash commands disabled (`HEADLESS_ARGS`) to avoid loading huge unrelated context. The binary is found via a login shell because a Finder-launched app has a minimal PATH. Only model ids in `claude::MODELS` ever reach `--model`; the choice is persisted in the `settings` table. Chat continuity uses the CLI session id stored in `chat_sessions`.
- **JSON envelope protocol** (`chat.rs`): the system prompt forces Claude to reply with one JSON object `{reply, scenes, story_text}`. `parse_envelope` tolerates plain-text replies and never lets an empty scene list wipe scenes. System prompt = base protocol + `prompts/audience.md` + the story's writing profile body.
- **Writing profiles** (`profiles.rs`, `prompts/profiles/*.md`): built-ins (`fairy_tale`, `novel`) are embedded with `include_str!`; users can add custom `.md` files (id prefix `custom:`, size-capped) to `<workspace>/profiles`. Per-story `story_settings` (profile, audience age group, target minutes) feed the prompt; `stats.rs` computes word/minute stats. `prompts/NOTICE.md` records the licensed sources the profiles were adapted from and is not sent to Claude.
- **Revisions and confirmation** (`actions.rs`, `db.rs`): state-changing operations snapshot the previous state into `revisions` (kinds `story_text`, `scenes`) so they can be rolled back. Claude's `story_text` is stored as a pending `proposal` on a message and applied only when the user accepts it; the outcome is queued in `pending_notes` and prepended to the next user message as `<app_notes>` so Claude knows what happened outside the chat.
- **Storage** (`db.rs`): SQLite via `rusqlite` (bundled), schema as plain `CREATE TABLE IF NOT EXISTS` statements. There is no migration framework, so changes to existing tables need manual `ALTER` handling.
- Errors are a single `AppError` (`error.rs`) serialized to the frontend.
- **Video-size images** (`upscale.rs`): a finished scene image can be enlarged to 1080p / 4K with the bundled Upscayl CLI (`digital-art-4x` model, run at 2x / 4x) and then fitted exactly by ffmpeg (cover-scale + centre crop). It runs only on a button press (per scene row, or "all" in the media panel; `upscale_images` command), is free and local (~25 s per image) and writes `<image name>-1080p.png` / `-4k.png` next to the source; `list_assets` finds them by file name, there is no DB column. The Upscayl binary and model are not in git: run `scripts/fetch-upscayl.sh` once (checksum-pinned) before `pnpm tauri dev/build`; Tauri bundles `src-tauri/resources/upscayl` as `upscayl/`. ffmpeg is the user's own (found via the login shell). `cargo test -- --ignored` runs the real-tools test.
- **Video export** (`video.rs`): `export_video` (media panel, "Собрать видео 1080p/4K") needs every scene to have a finished image and narration. Per scene it renders a clip with a sub-pixel smooth zoom/pan (ffmpeg `perspective`, not `zoompan`, which jitters; motion cycles zoom in / pan right / zoom out / pan left by position) from the biggest enlarged copy of the image, cached in `<media>/export/clip-<pos>-<hash>.mp4` so editing one scene re-renders only it; then one ffmpeg run joins the clips with 1 s `xfade fade` and mixes each narration in (0.5 s lead, 0.5 s tail). Result `video-1080p.mp4` / `video-4k.mp4` in the story's media folder, found by file name. Slow (about 2-5 s of render per second of video): the command blocks until done but emits `export-progress` events (percent, stage, scene; from ffmpeg's `-progress` frame counter, the final join weighted 0.4) that `ExportProgress.tsx` shows as a bar with the time left and a «Отменить сборку» button (`cancel_export` sets a shared `AtomicBool`; `run_ffmpeg` checks it on every progress line, kills ffmpeg and the half-written `.part.mp4` is removed; the cancelled export returns normally, finished clips stay cached so the next run resumes). ffmpeg/ffprobe come from the login shell. `cargo test -- --ignored` runs the real-ffmpeg tests.
- **Media bridge** (`media.rs`, `SceneMedia.tsx`): scene images and narration are generated in ElevenLabs Flows, which only Claude Code can reach (ElevenLabs connector); the app cannot. The app queues requests in `scene_assets` (status `requested`, keyed by story + scene *position*, with `source` = the scene text / image prompt it was requested for, used to flag stale assets). Optional per-scene custom references live in `scene_references`. Credit prices in `media::IMAGE_MODELS` / `SPEECH_CREDITS_PER_CHAR` are snapshots measured with `estimate_only` (see `PRICES_MEASURED_ON`); refresh them when they drift.

## Fulfilling queued media requests (when the user says "сделай очередь")

DB: `~/Library/Application Support/com.audiobooks.app/audiobooks.db`; files go in `<same dir>/media/<story_id>/`.

1. `sqlite3 <db> "SELECT story_id, position, kind, source, model_id FROM scene_assets WHERE status='requested' ORDER BY story_id, position"`. For `image` rows `source` is the prompt and `model_id` the Flows image model; for `audio` rows `source` is the narration text, `model_id` is `eleven_v4` and `voice_id` the narration voice (fairy-tale stories default to Ana-Rita2, other profiles to Hannibal; the user can pick from `media::VOICES`). Add `voice_id` to the SELECT.
2. Two phases. **"оцени очередь"**: for every requested row run `estimate_only` with its real text/prompt, voice and model (one flow per story: `creative_create_flow` first, pass its `flow_id` to every call). Ask once how many variants per item the user wants (the connector default produces several and costs several times more) and use that `generations_count`. Write each price with `UPDATE scene_assets SET estimate_credits=? WHERE story_id=? AND position=? AND kind=?`, report the total and **stop**. **"запускай"**: only after the user approves, generate the estimated items. Right before launching run `UPDATE scene_assets SET started_at=CURRENT_TIMESTAMP` for those rows so the app shows «генерируется…». The user may ask for one scene at a time ("запусти первую сцену", then "дальше"); then scene N's image uses the approved scene 0 image as a reference.
3. Images: scene 0 is the anchor; wire its finished image into later scenes as a reference, unless the story has characters (`story_characters`, see `characters.rs`): then wire in the pictures of the characters not switched off for the scene (`scene_character_off`) instead of the anchor. If the scene has a row in `scene_references`, wire that file in as well (upload via `creative_create_asset_upload`).
4. Download results to a **new** filename each time, `scene-<position>-<kind>-v<N>.<ext>` (the webview caches by URL), then `UPDATE scene_assets SET status='ready', file_path=<abs path>, credits=<spent>, error=NULL, updated_at=CURRENT_TIMESTAMP WHERE story_id=? AND position=? AND kind=?`. On failure set `status='failed'` and `error`. Touch no other table; the app polls and shows the result.
